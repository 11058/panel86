# ADR-0002. Привязка сущностей в рантайме: план A и план Б

**Статус:** РЕШЕНО 05.09.2026 — план A проверен на живом железе и работает.
План Б отменён.

## Контекст

Ключевое ограничение ESPHome для нашей задачи: список подписок на сущности
Home Assistant формируется при компиляции, отписки в протоколе нет.

Раскладка же приезжает в рантайме, и набор сущностей известен только после
загрузки `layout.json`.

## План A — через нативный API ESPHome

Отправлять `subscribe_home_assistant_state` **после старта**, когда раскладка
уже прочитана. Смена раскладки → переподключение к API (порядка секунды).

Плюсы:

- Никакого долгоживущего токена на устройстве.
- Одно соединение, уже зашифрованное.
- Устройство остаётся нормальным ESPHome-устройством в реестре HA.
- Подписка поштучная по природе протокола, то есть отфильтрована всегда.
- Если получится — это кандидат в апстрим ESPHome, и слой перестаёт быть нашим.

**Это гипотеза.** Отправку подписки после установления соединения никто
не проверял. Спайк на 3–5 дней, стоит вторым в дорожной карте — до того,
как написана хоть строка UI-VM.

## План Б — свой WebSocket к Home Assistant

Ровно то, что делает BETTA. Работает гарантированно.

Замерено на живом сервере 27.08.2026 (HA 2026.8.3, 1271 сущность,
см. `docs/02-ha-survey.md`):

| | |
|---|---|
| `subscribe_entities` без фильтра | 319 КиБ на 1271 сущность |
| `subscribe_entities` с `entity_ids` | 4 108 Б на 17 сущностей (241 Б на штуку) |
| Поток по фильтрованной подписке в простое | **0 сообщений за 120 с** |

**Фильтр по `entity_ids` работает** — разница в 80 раз. Панель обязана
подписываться списком из `layout.json`, а не целиком. Страница на 8 карточек —
около 2 КиБ, и после старта трафика нет вовсе.

Минусы: долгоживущий токен на устройстве, второе TCP-соединение, свой парсер
стейт-машины HA.

## Решение

Начинать с A. Держать Б наготове — его стоимость известна и ограничена,
на остальную архитектуру он не влияет: меняется только транспорт под UI-VM.

Интерфейс внутри UI-VM спроектировать так, чтобы транспорт подменялся,
а не пронизывал всю логику.

# Результат спайка, 5 сентября 2026

Проверено на живой панели против рабочего Home Assistant 2026.8.3.
Пакет проверки: `firmware/packages/spike-runtime-binding.yaml`.

## Вердикт: план A работает

**Подписка на произвольную сущность HA в рантайме возможна.** Своего
WebSocket, долгоживущего токена и парсера стейт-машины не нужно.

### Как это выглядит в цифрах

Подписались в рантайме на `sensor.kca6watertower_pzem_voltage`, который
обновляется примерно раз в 1,6 с. Без переподключения — **тишина 20 секунд**.
Затем перезагрузили интеграцию в HA:

```
09:34:58.662  Home Assistant (10.1.20.5): disconnected
09:34:58.705  Home Assistant (10.1.20.5): connected        +43 мс
09:34:58.749  >>> ПРИШЛО СОСТОЯНИЕ: 230.5                  +44 мс
09:34:59.346  >>> ПРИШЛО СОСТОЯНИЕ: 230.199996948242
09:35:00.352  >>> ПРИШЛО СОСТОЯНИЕ: 229.199996948242
```

**Полный цикл — 87 миллисекунд.** Оценка «около секунды» из исходного
решения оказалась втрое пессимистичной.

### Механизм, из-за которого нужно переподключение

Из `api_connection.cpp`:

- HA присылает `SubscribeHomeAssistantStatesRequest` **один раз**,
  при подключении; обработчик ставит `state_subs_at_ = 0`;
- главный цикл шлёт подписки по одной, пока индекс не дойдёт до конца
  списка, после чего ставит `state_subs_at_ = -1` и замолкает навсегда;
- `state_subs_at_` приватный — обнулить снаружи нельзя.

Поэтому подписка, добавленная после подключения, ложится в вектор
и не уезжает. При переподключении HA снова запрашивает список — и получает
его целиком, уже выросший.

## Три ограничения, которые надо заложить в UI-VM

**1. Рантайм-часть API живёт за ifdef-ами — компонент включает их сам.**
`subscribe_home_assistant_state` спрятан за `USE_API_HOMEASSISTANT_STATES`,
`send_homeassistant_action` — за `USE_API_HOMEASSISTANT_SERVICES`. ESPHome
включает их только при **компилируемом** использовании: подписке через
`platform: homeassistant` или вызове `homeassistant.action`.

> Уточнение от 05.09.2026. Сначала это обходилось фиктивной
> «подпиской-якорем» в YAML. Оказалось, что оба флага — обычные
> `cg.add_define`, и компонент объявляет их сам:
>
> ```python
> cg.add_define("USE_API_HOMEASSISTANT_STATES")
> cg.add_define("USE_API_HOMEASSISTANT_SERVICES")
> ```
>
> Якорь не нужен, лишнего YAML у пользователя компонента тоже.
> Проверено: якорь удалён, всё продолжает работать.

**2. Отписаться нельзя.** Публичного способа очистить `state_subs_` нет,
вектор приватный. Список только растёт: каждое применение новой раскладки
добавляет подписки, не убирая старые.

**Решение: применение раскладки = перезагрузка панели.** Она и список
очищает, и заново подписывает всё из нового `layout.json`. Операция редкая,
загрузка занимает секунды — цена приемлемая.

**3. Переподключиться по своей воле устройство не может.** Штатного действия
нет. Значит механизм применения раскладки — именно перезагрузка, а не
изящное переподключение.

## Что стоит отдать в апстрим

Два маленьких патча закрыли бы оба ограничения и убрали бы перезагрузку:

- публичный `clear_state_subscriptions()` на `APIServer`;
- способ заново запустить рассылку списка на живом соединении
  (сброс `state_subs_at_` в 0).

Это ровно тот случай, о котором говорилось в ADR-0001: слой перестаёт быть
нашим навсегда. Пока обходимся перезагрузкой.
