# ADR-0003. Ethernet основным каналом, Wi-Fi резервом

**Статус:** пересмотрено 04.09.2026 — основным каналом выбран Wi-Fi.
Исходное решение и его обоснование сохранены ниже.

## Контекст

У связки ESP32-P4 + ESP32-C6 по SDIO в ESPHome есть открытая проблема ровно
на этой плате (esphome/esphome#10956): потери пакетов SDIO, повторные срывы
ассоциации, иногда паника. Устройство работает стабильно, если убрать Wi-Fi
из конфига.

Показательно, что и референсный конфиг `chrisdunnname` держит Ethernet
закомментированным и живёт на Wi-Fi — то есть проблему обходят, а не решают.

## Решение

Ethernet — профиль по умолчанию (`packages/net-ethernet.yaml`).
Wi-Fi — отдельный профиль, резерв (`packages/net-wifi.yaml`).

## Следствие для монтажа: профиль A

Раз кабель к панели всё равно нужен, из этого выжимается максимум:

**Один CAT5e: две пары под 100M Ethernet, две свободные пары под 24 В**
от блока питания в щитке.

Это решает сразу три задачи:

1. Обходит нестабильный Wi-Fi.
2. Убирает 220 В из подрозетника — безопаснее и проще по монтажу.
3. Ставит все панели дома на один ИБП в щитке.

Плата принимает 6–30 В, так что 24 В по витой паре подходит напрямую,
без модуля PoE PD (которого на плате нет).

**Профиль B** (панель физически заменяет выключатель, 220 В в коробке,
реле коммутирует нагрузку) остаётся для случаев, где иначе нельзя. Там
главный вопрос — глубина коробки: с модулем AC/DC нужно ≥ 60 мм.

## Что подтвердить в P0

- Воспроизводится ли #10956 на текущей версии ESPHome.
- Держит ли Ethernet соединение сутки без переподключений.
- Пины IP101 взяты из референсного конфига и на плате не проверялись.

# Пересмотр от 04.09.2026: основной канал — Wi-Fi, Ethernet резервом

## Что изменилось

Решение владельца проекта: **Wi-Fi основной, Ethernet остаётся вторым каналом.**

Практика перевесила: тянуть витую пару к каждому подрозетнику в уже
отделанном доме — отдельный проект со штроблением, а панелей планируется
несколько. Профиль A из исходного решения («один CAT5e с 24 В по свободным
парам») остаётся хорошей идеей для нового строительства, но не для этого дома.

## Как это сделано

ESPHome не разрешает объявить `wifi:` и `ethernet:` вместе — если только
оба не перечислены в блоке приоритетов:

```yaml
network:
  priority:
    - wifi        # держит маршрут по умолчанию
    - ethernet    # горячий резерв
```

Первый в списке получает высший приоритет установки и маршрут по умолчанию.
Проверено на 2026.8.2: конфигурация валидна.

Это лучше, чем две отдельные сборки: воткнули кабель — панель им и пользуется,
выдернули — ушла на Wi-Fi, и всё без перепрошивки.

## Чего это стоит

**1. Риск #10956 принят, а не устранён.** Известная нестабильность SDIO между
P4 и C6 никуда не делась, и теперь она на основном канале. Ethernet как резерв
смягчает последствия, только если кабель физически воткнут — иначе резерва нет.

Обязательно к проверке: сутки под нагрузкой с логом на предмет
`Dropping packet(s) from stream`, `Failed to push data to rx queue`,
повторных `Association Leave`.

**2. Боковая кнопка на GPIO35 потеряна навсегда.** Пока `ethernet:` есть
в конфиге, GPIO35 занят под EMAC_TXD1 — независимо от того, воткнут кабель
или нет. Отказ от Ethernet вернул бы кнопку, сохранение двух каналов её стоит.

На выбор:
- оставить оба канала и жить без аппаратной кнопки (текущий выбор);
- убрать `ethernet:` — вернуть кнопку, потерять резервный канал.

**3. Загрузка.** `Setup ethernet took 4352ms` при отсутствии кабеля.
Эти 4,3 секунды платятся при каждом старте ради резерва, которым, возможно,
никогда не воспользуются. Померить заново, когда Wi-Fi заработает: если
Ethernet инициализируется параллельно, цена может оказаться меньше.

## Развязка, 07.09.2026: Ethernet выключен по умолчанию

Оказалось, что объявленный, но не подключённый Ethernet не просто ждёт
кабель — он **активно мешает**: повторяет DHCP каждые 15 секунд и каждый
раз сбрасывает общие настройки сервера имён. Из-за этого не
синхронизировалось время и не открывался Home Assistant по имени,
и каждый случай выглядел отдельной поломкой.

Симптоматическое лечение (резервный DNS каждые 5 секунд) работало,
но было именно симптоматическим.

**Решение:** `enable_on_boot: false` в конфиге, а включение — из
веб-интерфейса, когда кабель действительно воткнут. Компонент ESPHome
даёт `enable()` и `disable()` в рантайме, так что интерфейс остаётся
в прошивке и доступен в любой момент.

Статический адрес задаётся через `esp_netif` по ключу `ETH_DEF`:
`set_manual_ip` у компонента защищённый. Применяется через полторы
секунды после подъёма, когда netif уже готов.

### Измерено до и после

| | было | стало |
|---|---|---|
| Попыток DHCP за минуту | 4 | 0 |
| Порча DNS за минуту | каждые 15 с | 0 |
| `Setup ethernet` | 4342 мс | **300 мс** |

Загрузка ускорилась на четыре секунды — это была вторая по величине
статья после Wi-Fi.

### Что это значит для ADR-0003

Оба канала по-прежнему в прошивке, приоритет за Wi-Fi. Разница в том,
что неиспользуемый интерфейс теперь по-настоящему спит, а не борется
за общие настройки стека.


### Проверено с кабелем, 07.09.2026

Ethernet включён из веб-интерфейса. Поднялся за 2,5 секунды,
100 Мбит/с, полный дуплекс, адрес по DHCP `172.16.1.66`,
шлюз `172.16.1.1`.

Панель отвечает **по обоим адресам одновременно** — `172.16.1.58`
по Wi-Fi и `172.16.1.66` по Ethernet, как и задумано блоком
`network: priority`.

**История с DNS закрыта полностью.** Отдельным опытом проверено: при
выключенном Ethernet Wi-Fi получает сервер имён сам —
`DNS1: 192.168.1.240`, время синхронизируется. То есть DNS исправно
приходил по DHCP всегда, а обнулял его именно неподключённый Ethernet.

Резервный `1.1.1.1` остаётся, но теперь ждёт полминуты подряд
без сервера имён, прежде чем вмешаться. Без этой выдержки он успевал
сработать в окне подъёма интерфейса и затирал настоящий адрес своим:
наблюдалось при первом включении Ethernet — DHCP выдал `192.168.1.240`,
а в настройках остался `1.1.1.1`.

Теперь это страховка для сетей, которые действительно не выдают DNS,
а не обход собственной ошибки.
