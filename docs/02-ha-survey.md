# Разведка боем: что показал живой Home Assistant

Замеры сделаны 27 августа 2026 против рабочего сервера (HA 2026.8.3) по
WebSocket API — тем самым каналом, который в концепте назван «планом Б».
Скрипт: `tools/ha_probe.py`. Токен в репозиторий не попадает.

Три результата меняют план. Остальное — контекст.

---

## 1. Фильтрованная подписка обязательна, и она работает

| Что подписываем | Первый снапшот | Сущностей | На сущность |
|---|---|---|---|
| `subscribe_entities` без фильтра | **319 КиБ** | 1271 | 257 Б |
| `subscribe_entities` с `entity_ids` | **4 108 Б** | 17 | 241 Б |

Разница — **в 80 раз**. Панель обязана подписываться списком, а не целиком:
разбирать 319 КиБ JSON на старте ради восьми карточек на экране — впустую
потраченные и память, и секунды загрузки.

**Следствие для UI-VM:** список `entity_ids` собирается из `layout.json` при
загрузке раскладки. Страница на 8 карточек — около 2 КиБ. Это ничто.

**Следствие для плана A** (подписка через нативный API ESPHome): там подписка
и так поштучная, то есть отфильтрована по природе протокола. Ещё один довод
проверять его первым.

## 2. Трафик пропорционален экрану, а не размеру установки

`subscribe_entities` — это **push**: Home Assistant сам присылает событие
в момент изменения. Опроса нет ни с какой стороны.

Два замера, и вместе они говорят больше, чем каждый по отдельности.

**Комната, в которой ничего не происходит** (Веранда, 17 сущностей):
0 сообщений за 120 секунд. Присылать было нечего — свет никто не трогал,
уставки стояли, температура не сдвинулась.

**Пять заведомо активных датчиков** (напряжение, уровень бака, нагрузка,
два датчика дыма): **46 обновлений за 45 секунд**, каждое ~160 байт,
приходят сами:

```
+ 1.6 с  sensor.kca6watertower_pzem_voltage      -> 231.5
+ 2.0 с  sensor.kca16homemcu1_smoke_ch1_voltage  -> 0.817
+ 3.5 с  sensor.kca6frontyard_currentload        -> 8.10
```

Для сравнения, поток по всей установке целиком гуляет от 231 Б/с до 3,8 КиБ/с
в зависимости от окна — его гонят 379 сущностей `image` и 18 камер, ни одна
из которых панели не нужна.

**Вывод:** сетевая нагрузка панели определяется тем, что на экране, а не тем,
сколько сущностей в доме. При 1271 сущности и 2019 записях в реестре панель
работает так же, как работала бы при полусотне.

### Из этого же теста вылезла проблема

`sensor.kca6watertower_pzem_voltage` шлёт обновление **раз в 1,6 секунды**,
и **88 % изменений меньше 0,5 В** при общем разбросе 228,3–231,5 В.
Это шум АЦП, а не информация.

Карточка с таким датчиком будет перерисовываться раз в полторы секунды
до скончания века. Последствия хуже, чем кажется:

- LVGL никогда не уходит в простой — растёт и потребление, и нагрев
  в закрытом подрозетнике;
- экран не может уснуть по-настоящему;
- пользователь видит дёргающиеся цифры, которые ничего не значат.

**Решение — в формате раскладки.** У карточки-датчика появились `deadband`
(не перерисовывать, пока изменение меньше порога) и `throttle` (не чаще, чем
раз в N), плюс блок `defaults` на всю раскладку со значениями по умолчанию
`throttle: 1s` и `deadband_percent: 0.5`.

Это тот случай, когда подавление ставится по умолчанию, а отключается
осознанно, — а не наоборот.

## 3. Комнаты почти не заполнены — и это блокер

| | Сущностей |
|---|---|
| Всего в реестре | 2019 |
| Скрытые и отключённые | 772 |
| Видимых | 1247 |
| Из них привязано к комнате | 97 |
| **Без комнаты** | **1150 (92 %)** |

Вся концепция «панель знает, в какой она комнате» стоит на реестре областей.
Сейчас он заполнен на 8 %.

Это не проблема прошивки — это работа в Home Assistant, и её надо сделать
**до** того, как писать UI-VM, иначе разработку не на чем проверять. Хорошая
новость: почти все сущности приходят с устройств, а устройству область
назначается один раз и наследуется всеми его сущностями. Устройств всего 109.
Реально это вечер работы, а не неделя.

## Что из этого следует для каталога карточек

Концепт писался под квартиру. Дом с участком выглядит иначе.

**Добавить в каталог:**

- **`valve`** — поливалка на газоне. В квартире такого типа нет вовсе, здесь он
  на главном экране. Добавлен в схему.
- **`camera`** поднимается в приоритете: 17 камер, NVR с детекцией человека
  (`binary_sensor.ch2_cam02_person_detected`), события тревоги. Аппаратный
  JPEG-декодер P4 из «приятного бонуса» становится профильной функцией.
- **`alarm`** — 5 панелей `alarm_control_panel`. Значит, нужен и экран
  с кодовой клавиатурой.

**Не добавлять:** отдельного типа под водонапорную башню не нужно. Она целиком
собирается из `switch` + `sensor` — см. `examples/ogorod.layout.json`. Это
проверка того, что каталог из десяти типов действительно покрывает реальность.

## Мусорные сущности: редактор обязан фильтровать по умолчанию

Каждый выключатель на ESP8266 отдаёт в комнату три лишние сущности:

```
light.esp8266sw1_status_led     <- светодиод на плате
binary_sensor.esp8266sw1_ha_status  <- связь с HA
binary_sensor.esp8266sw1_button1    <- физическая кнопка
```

В «Гостиной» из 15 сущностей на панель просятся 6. Если показать в выборщике
всё подряд, настройка снова превратится в мучение — ровно то, за что ругают
предшественников.

**Решение:** редактор по умолчанию скрывает сущности с `entity_category`
`config` и `diagnostic` (это поле есть в реестре), плюс `*_status_led`.
Галочка «показать всё» — есть, но выключена.

## Как повторить замеры

```bash
export HA_WS="wss://ваш-хост/api/websocket"
export HA_TOKEN="долгоживущий токен"        # НЕ коммитить
export HA_CA="$(python3 -m certifi 2>/dev/null || echo /etc/ssl/cert.pem)"
python3 tools/ha_probe.py
```

На macOS с python.org-сборкой проверка сертификатов падает — системное
хранилище выгружается так:

```bash
security find-certificate -a -p \
  /System/Library/Keychains/SystemRootCertificates.keychain > roots.pem
export HA_CA=roots.pem
```
