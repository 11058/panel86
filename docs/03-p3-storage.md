# P3, этап 1: хранилище раскладки

Раскладка интерфейса должна лежать на панели как **данные** и меняться
без пересборки прошивки — в этом вся суть проекта (ADR-0001). Первый
этап P3 — слой хранения. Сделан и проверен на живой панели 5 сентября 2026.

## Своя таблица разделов

Штатная таблица ESPHome отдаёт всё под две OTA-области по 16,5 МБ
и не оставляет места под данные. При образе в 1,6 МБ это расточительство.

`firmware/partitions.csv`:

| Раздел | Начало | Размер |
|---|---|---|
| nvs | 0x009000 | 28 КиБ |
| otadata | 0x010000 | 8 КиБ |
| phy_init | 0x012000 | 4 КиБ |
| app0 | 0x020000 | 6 МБ |
| app1 | 0x620000 | 6 МБ |
| **storage** (LittleFS) | 0xC20000 | **19,88 МБ** |

Образ занимает 1,6 МБ из 6 МБ — запас почти четырёхкратный даже с учётом
шрифтов и картинок, которые появятся в P3.

> **Смена таблицы разделов не проходит по OTA** — работающий загрузчик
> читает старую таблицу. Прошивать только по USB. NVS при этом стирается,
> сохранённые данные Wi-Fi теряются.

## Компонент panel_ui

`components/panel_ui/` — внешний компонент ESPHome. Пока это только слой
хранения; интерпретатор JSON в дерево LVGL — следующий этап.

В ESPHome **нет ни LittleFS, ни SPIFFS**, поэтому LittleFS подтягивается
как управляемый компонент ESP-IDF из реестра:

```python
add_idf_component(name="joltwallet/littlefs", ref="1.16.4")
```

Запись атомарная: во временный файл, затем переименование. Обрыв питания
посреди сохранения не должен оставить панель с половиной раскладки.

## Засада: remove() и rename() возвращали ENOSYS

Первый же тест записи упал:

```
rename('/fs/layout.json.tmp' -> '/fs/layout.json') = -1,
errno=88 (Function not implemented)
```

Причина рукотворная: **ESPHome по умолчанию вырезает операции с каталогами
из VFS ради экономии флеша** — опция `disable_vfs_support_dir` со значением
`True` по умолчанию. Без них на LittleFS нельзя ни удалить файл,
ни переименовать, то есть атомарное сохранение невозможно в принципе.

Правильное лечение — не флаг в YAML пользователя, а объявление потребности
самим компонентом:

```python
from esphome.components.esp32 import require_vfs_dir
require_vfs_dir()
```

Это перебивает отключение и ставит `CONFIG_VFS_SUPPORT_DIR=y`. Пользователю
компонента ничего делать не надо — так и должно быть.

# Этап 2: интерпретатор и управляющий канал

## Раскладка становится экраном

`layout.json` разбирается ArduinoJson (через компонент `json` ESPHome)
и превращается в дерево LVGL: сетка из карточек с названием, значением
и цветом рамки по типу.

Управляемые типы (`light`, `switch`, `valve`) реагируют на касание и шлют
`<домен>.toggle` через `send_homeassistant_action`. Датчики не кликабельны.

Подписки на сущности строятся из самой раскладки — отдельно их описывать
не нужно, ровно как задумывалось в концепте.

## Управляющий канал: заливка по HTTP

Свой сервер на `esp_http_server`, а не `web_server` ESPHome: тому нельзя
добавить свои маршруты.

| | |
|---|---|
| `GET /layout.json` | отдать текущую раскладку |
| `POST /layout.json` | проверить, сохранить, перестроить экран |

**Проверка до записи.** Присланное сначала разбирается и проверяется
на наличие `pages`, и только потом попадает на диск. Испорченный JSON
не должен затирать рабочую раскладку.

Проверено на живой панели:

```
POST валидной раскладки  -> {"saved":583,"cards":4,"rebuilt":true}
POST мусора              -> HTTP 422
POST JSON без pages      -> HTTP 422
GET после отказов        -> прежняя раскладка на месте
```

Верхняя граница на размер тела — 64 КиБ: без неё большой запрос съест
память панели.

## Засада: httpd нельзя поднимать в setup()

Первая версия запускала сервер в `setup()` и получила цикл перезагрузок:

```
assert failed: xQueueSemaphoreTake queue.c:1709 (( pxQueue ))
```

Причина: `setup_priority::DATA` отрабатывает раньше сетевого стека,
а `httpd_start` создаёт сокет. Лечение — ленивый запуск в `loop()`
при первом появлении сети через `network::is_connected()`.

## Что работает целиком

При загрузке: раскладка читается с LittleFS, строится экран, оформляются
подписки. Дальше правка прилетает по HTTP и экран перестраивается
за доли секунды — **без пересборки и без перепрошивки**. Это и есть
основной тезис проекта (ADR-0001), проверенный на железе.

## Засада: белый экран при исправных логах

После перехода на многостраничность экран стал полностью белым — при том,
что в логах всё было идеально: страница показана, 14 карточек построено,
демо-режим заполнил их, ошибок LVGL нет.

Причина: **у `lv_obj` заливка по умолчанию светлая**, а своей нигде задано
не было. Белый фон контейнера просто перекрывал всё построенное.

Урок общий: при работе с LVGL из кода нельзя полагаться на умолчания темы —
фон и цвет текста надо задавать явно каждому создаваемому объекту:
контейнеру, странице, карточке, каждой метке. Иначе отладка уходит
в поиск логической ошибки там, где её нет.

## Верхний слой LVGL: одна клавиатура на всё устройство

Клавиатура была виджетом страницы, и для второго поля ввода понадобилась
вторая — что вешало прошивку по сторожевому таймеру. Это был симптом,
а не причина: клавиатура должна быть **одна на устройство** и всплывать
там, где нужна.

Решение — `lv_layer_top()`. Объекты верхнего слоя рисуются поверх любой
страницы, поэтому туда вынесены:

- **клавиатура** — одна, показывается скриптом `kb_show` с указанием поля,
  прячется `kb_hide`;
- **статусная строка** — видна везде, включая настройки;
- **ловец пробуждающего касания** — прозрачный слой во весь экран,
  появляется при погасании. Первое касание после сна только будит панель
  и не доходит до карточки под ним: иначе спросонья выключаешь свет,
  который не собирался трогать.

Виджеты объявлены в YAML на рабочей странице и переносятся наверх
при загрузке через `lv_obj_set_parent` — так сохраняются их идентификаторы
и вся привязка из YAML.

## Оформление страниц: три подхода и почему победил третий

**Список в скрипте.** Проход по перечисленным страницам при загрузке.
Работает, но список отстаёт от конфигов: при добавлении страницы про него
забывают. Так расписание осталось с белым фоном.

**Самоокраска через `on_load`.** Каждая страница красит себя при показе,
забыть нельзя. Но `on_load` срабатывает, когда страница **уже отрисована**:
первый показ выходит белым, второй — правильным. Со стороны выглядит как
мигание при каждом первом входе в раздел.

**Список, собираемый из конфигов** — `tools/gen_page_list.py`. Сканирует
`- id: page_*` во всех YAML и вписывает массив между маркерами в
`theme-fix.yaml`. Красит всё до первого показа и не может отстать:
забыть новую страницу теперь можно только вместе с забытым запуском
генератора, а это видно в diff.

`on_load` оставлен как страховка — он полезен при смене темы на лету.

## Главная засада: LVGL не потокобезопасен

Перестроение интерфейса выполнялось прямо в задаче веб-сервера — там же,
где обрабатывается `POST /layout.json`. Одновременно главный цикл рисует
те же объекты через `lv_timer_handler()`.

Долгое время это сходило с рук: карточки были простыми, окно гонки узким.
С появлением иконок, переходов стилей и анимаций окно выросло, и посыпалось
всё сразу: карточки исчезали с экрана, веб-сервер принимал соединение,
но переставал отвечать, панель уходила в перезагрузку.

**Правило: из задачи веб-сервера LVGL трогать нельзя.** Обработчик только
пишет файл и ставит отметку `request_rebuild()`, а работу делает `loop()`
в главном цикле:

```cpp
void PanelUI::loop() {
  if (this->rebuild_pending_) {
    this->rebuild_pending_ = false;
    this->rebuild();
  }
  ...
}
```

Побочно это выявило вторую тонкость: несколько отправок подряд дают
перестроение по файлу, который в этот момент переписывается следующей
отправкой. Счётчик карточек скачет. Для редактора это безобидно — человек
не жмёт «отправить» три раза в секунду, — но если появится автосохранение,
отправки надо будет объединять по времени.

## Анимации и почему они ломались

Карточка создавалась прозрачной и проявлялась анимацией. При перестроении
`lv_obj_clean()` удалял объекты, а анимации на них оставались жить —
и новые карточки могли остаться прозрачными. Выглядело как «все карточки
слетели с экрана».

Лечение из двух частей: `lv_anim_delete_all()` перед очисткой, и появление
показывается **только при первом построении**. Правка из редактора должна
применяться мгновенно, а не переигрывать анимацию на каждое сохранение.

## Камеры: работает, но дорого

Кадр с камеры берётся у Home Assistant через `/api/camera_proxy/<сущность>`
компонентом `online_image`, декодируется программно (JPEGDEC) и рисуется
в карточку. Адрес и токен — из того, что панель сохранила у себя.

**Замерено на живой панели:**

```
Image fully downloaded, 192464 bytes in 5242 ms
online_image.image took a long time for an operation (4852 ms), max is 2550 ms
Image size: 960 x 1280, bpp: 24
```

Пять секунд на кадр, и всё это время главный цикл занят — панель
не реагирует на касания. Поэтому интервал обновления 30 секунд,
а не 10, и камер в пуле всего две.

Что с этим делать по-настоящему:

- **отдавать кадр поменьше.** 960×1280 показывается в карточке 340×200 —
  декодируется впятеро больше, чем нужно. У большинства камер есть второй
  поток низкого разрешения, его и надо отдавать в Home Assistant;
- **аппаратный декодер JPEG у P4.** Он есть в железе и был одним из доводов
  за эту плату, но ESPHome его не использует. Свой декодер — отдельная
  работа, зато она же снимет и блокировку цикла.

Пока камера пригодна как «взглянуть на двор», а не как постоянно живой
кадр на экране.
